# 同步后提取与审核知识

Linear 和 GitHub 连接器在完整快照同步成功后，可以自动提取指标定义与共享业务规则。
提取结果先进入“待审核”；只有管理员批准的条目才进入正式知识和 Agent 检索。
不会生成已验证 SQL、实体或关系，也不会修改人工维护的模型业务背景。

## 开启与日常使用

- 新建连接默认开启。升级前已有连接保持关闭；组织 owner/admin 可在知识来源卡片开启并补跑现有资料。
- 卡片分别显示来源同步状态和提取状态；单条来源显示处理进度、待审核数量和失败重试入口。
- “补跑现有资料”按来源内容指纹与提取版本去重。已完成的同版本任务不会重复调用 AI，也不会重新生成已驳回的同版本建议。
- 关闭自动提取会取消未完成任务，保留已有草稿和正式知识。重新开启可恢复当前来源版本的任务。
- 同步与提取相互独立：AI 调用失败不影响已成功同步的原文。

提取使用组织或全局现有的后台 AI 配置、网关、配额和用量记录。无需新增 Key；后台不借用浏览器会话。
当前仅支持服务端可直接使用的模型配置，只有交互会话可用的云代理不能执行后台任务。
缺少配置或配额不足时任务暂停，修复后点击重试。临时网络、限流和服务故障每轮最多尝试五次。
每个分片最多进行一次格式修复；修复仍不合格时整篇失败，不保存部分草稿。

## 审核指标与业务规则

在模型的“待审核”入口查看建议、原文证据、原文链接及现有条目内容。可以编辑、批准、驳回，
或批量批准无冲突且映射完整的新增建议。同名不同口径需逐条审核，明确选择修改目标或另建条目。
修改现有条目保留原 ID。若来源或正式条目在审核期间变化，保存会被拒绝，需要重新加载审核。

指标必须选择模型已关联的数据源。填写表、字段、表达式或过滤条件时，会使用该连接的 Schema 元数据校验；
不执行文档中的 SQL。只有文字计算口径、没有表达式的指标可保留文字定义，不能充当可执行字段映射。
业务规则可作用于整个模型、指定数据源或指定指标，无需伪造表字段。指定指标范围在未选择指标时不能发布，也不会隐式成为全局约束。

批准的业务规则在独立“业务规则”列表展示，可编辑或停用。已停用条目不参与 Agent 检索。
来源列表资产计数、知识关系图及 Agent `search_assets` / `read_asset` 包含已审核业务规则与来源引用。
草稿只对管理员开放，不会通过正式定义或 Agent 资产接口泄漏。

## 语义模型与业务规则

“语义模型”保存结构化实体、维度、关系与指标。指标的计算、分母和专属条件保留在指标中；
只有明确适用于多个指标或全局的约定才独立保存为“业务规则”。例如测试订单仅从净收入中排除时，
它属于净收入的专属条件；支付失败订单排除可关联净收入和订单数，不能改变支付成功率按全部支付尝试计数的分母。

指标详情显示适用的已审核规则及停用提示，可编辑引用并跳转到规则。规则列表显示适用范围、关联指标、
反向引用数量与来源证据，可跳转回指标。模型和数据源规则在其范围内自动生效，指定指标规则只对显式关联的指标生效。
规则正文只维护一份，管理员保存或审核通过更新后，引用处读取最新版；不会改写指标的 SQL、表达式或人工过滤条件。
停用规则停止其作用，已有引用保留提示；删除指标只清理关联，保留规则。

来源 AI 提取结果先暂存，由独立的持久化模型整理任务综合完整结果、未审核草稿和正式知识整理分类、重复与引用。
所有输入必须被完整保留在整理结果中，证据来自原始版本；失败保留旧草稿，可在“待审核”点击“整理待审核草稿”重试。
共享范围不确定时保留为指标条件或等待管理员明确范围，不自动扩大为全局规则。
新指标依赖未发布规则时，审核窗口同时显示依赖规则及证据，一起事务发布；也可以明确把该条件保留在指标内。
存在冲突时必须明确选择目标。审核再次校验来源、正式条目、规则及引用版本。

Agent `read_asset` 读取指标时返回有效规则、适用范围、版本和原文引用。指定指标规则只进入对应指标的上下文，
资产引用版本及运行记录包含所用规则版本。草稿、未关联的指定指标规则与已停用规则不会作为正式有效约束使用。

## 来源更新、删除与恢复

来源正文更新或删除时，正式知识继续保留并标记来源变化／失效，同时产生复审建议。
管理员可以保留旧知识、停用旧知识，或审核新提取结果并明确更新原条目。AI 不会自动覆盖人工编辑。
旧版本任务不能写入新来源版本；不同文档的相同结构化结果合并证据，口径不一致时保留冲突。
已保存的摘录、原文 URL、来源指纹和审核信息不会随原文删除而丢失。Agent 读取过期知识时会收到来源状态。
为已发布条目添加新文档证据也会产生待审核更新；审核前不改变正式引用。多文档合并草稿中的一篇原文变化时，
仍由其他当前文档独立支持的建议会继续保留，避免丢失未变化文档的提取结果。

全文按段落、Markdown 边界与上下文预算分片，遍历到末尾，表格与代码块尽量保持上下文。
超出模型上下文或输出预算时进一步拆分。AI 选择原文片段编号，服务端保存对应的原文摘录并验证；
缺失、伪造或无法匹配的证据会使整篇失败。全部分片成功后才保存暂存结果；模型整理全部成功后才事务提交草稿。
文档作为不可信参考资料处理，不授权 AI 执行其中的指令、SQL 或外部动作。

## 运行与升级

Postgres 与 PGlite 应用 `0034_knowledge_extraction`，PGlite 编译迁移包包含同一变更。
它新增任务、草稿、业务规则及证据表，已有连接的 `auto_extract` 默认为 false。
随后应用 `0035_knowledge_rule_scopes`（Postgres / PGlite SQL 对齐，编译包已更新），增加规则范围、稳定指标引用及模型整理队列。
已有正式规则依照当前数据源配置迁移范围，不改变内容、ID、审核历史或自动提取开关，不自动建立指标关联。
迁移为已有未审核草稿安排一次整理；旧草稿在完整成功替换前保留。已发布内容的分类调整仍需审核，驳回版本不会由整理重新发布。
使用正常数据库启动迁移流程，部署时一并更新所有服务实例，并重启 worker。

Web / Docker 需要持续运行的 Node 服务。worker 启动即扫描，之后每分钟扫描；
数据库认领、两分钟租约和每三十秒心跳支持多实例及重启恢复。
Desktop 使用同一应用和队列，运行期间处理，关闭／休眠后在恢复运行时继续处理未完成任务。
不需要保持知识页面打开。生产部署不适用于请求结束即退出的临时 serverless 实例。

## 接口

管理动作仅限组织 owner/admin，读取沿用模型权限：

- `knowledge.setAutoExtraction`、`knowledge.retryExtraction`、`knowledge.getExtractionStatus`
- `knowledge.organizeCandidates`、`knowledge.updateMetricRules`、`knowledge.reviewCandidateBundle`
- `knowledge.listCandidates`、`knowledge.getCandidate`、`knowledge.reviewCandidate`、`knowledge.approveCandidates`
- `knowledge.listBusinessRules`、`knowledge.getBusinessRule`、`knowledge.updateBusinessRule`、`knowledge.getAssetEvidence`

Action 请求继续使用现有 `/api/actions/execute` 入口；不提供绕过审核的自动发布接口。

测试与真实电商验收记录见 [提取验收](testing/knowledge-extraction-acceptance-cn.md)。
